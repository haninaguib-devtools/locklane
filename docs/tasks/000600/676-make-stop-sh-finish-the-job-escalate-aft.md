# 676 — Make stop.sh finish the job: escalate after the grace period and report the state it found
Issue: #676

## Asked
`stop.sh` (generated by `install.sh`/`update.sh`, `write_control_scripts`) does not
always leave the server stopped, and when it fails it does not say enough to tell why.
On macOS, `launchctl bootout` unloads the agent and sends the JVM SIGTERM; the script
then waits up to 30s for both the agent to leave the domain and the pid to exit, and
exits 1 with "did not stop within 30s" if either is still there — leaving the JVM still
winding down with nothing done about it. The detached fallback has the same shape.
`systemctl --user stop` on Linux does not have this problem: systemd escalates to
SIGKILL after its own timeout. Separately, the console-tab refusal (#647) reads as a
failure rather than a refusal, and a failure prints no state.

Make the launchd and detached paths finish the job the way systemd does: after the
grace period, SIGKILL the pid (and, for launchd, `launchctl kill SIGKILL` the service
if it is still in the domain), wait a bounded few seconds more, and only then report —
exit 0 with "forced" when it is gone, exit 1 with the pid, the agent's domain state and
the surviving children when it is not. Keep the refusal, but make its first line say
"not run" and name the console tab and the IDE terminal.

## Done when
- launchd path, with a stub `launchctl` whose `print` keeps reporting the service and a
  stub pid that ignores SIGTERM: `stop.sh` exits 0, the pid is gone, and the output
  contains "forced".
- Detached path, with a pid that ignores SIGTERM: `stop.sh` exits 0, the pid is gone,
  the pid file is removed, and the output contains "forced".
- Both paths, with a pid that survives SIGKILL: exit 1, and the output names the pid and
  its domain/pid-file state.
- The refusal's first line reads "not run" and names the console tab and the IDE
  terminal; exit code stays 2.
- `write_control_scripts` in `install.sh` and `update.sh` stay byte-identical.
- `./.t-workflow/scripts/consistency-check.sh` passes.

## Explicitly not
- Changing what the engine does on SIGTERM (PTY/code-server teardown) — if the JVM
  routinely takes >30s to exit, that is its own engine issue.
- The systemd path, which already escalates.

## Decisions made along the way
- The same escalation is applied to `stop_launchd_agent` (the stop `install.sh` and
  `update.sh` themselves run before swapping the jar), so an update over a JVM that
  ignores SIGTERM no longer aborts with the jar left un-swapped (Claude, 2026-09-04).
- The refusal wording is changed in **both** copies of the message — the generated
  guard (`write_inside_server_guard`) and the scripts' own top-level
  `refuse_inside_server` — because the code's own rule ("kept in step by hand — a
  change to one is a change to both") outranks a narrow reading of the Scope line; the
  refusal a person sees from `install.sh` and from `stop.sh` now reads the same.
- "A pid that survives SIGKILL" cannot be a stub `kill` (a bash builtin, not on PATH):
  the harness uses a zombie — a forked child its parent never reaps — which `kill -0`
  reports alive and SIGKILL cannot remove. That is also the one real-world shape this
  branch covers: a process launchd still lists but nothing can signal away.
