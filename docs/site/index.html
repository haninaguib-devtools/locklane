locklane

An IDE for the AI age

Work several initiatives at once, without losing your place in any of them.

Work is represented as GitHub issues or Jira tickets — whatever a team already tracks in. The developer stays the product manager and designer, deciding scope and direction; agents (Claude, Codex, or a plain shell) do the implementation, each in its own git worktree so parallel initiatives never collide. Every console is a long-lived terminal that keeps running after the tab closes, reattachable from any browser.

Principles

Built for parallel work, not one task at a time

Several initiatives, one workspace — every issue is its own node in the tree, with its own consoles, so switching to one never loses your place in another.

The developer is the product manager and designer — deciding scope and direction, while an agent does the implementation in each console.

Issues are the unit of work — a GitHub issue or Jira ticket, not a locklane-specific task format.

Worktrees keep parallel agents out of each other's way — each console runs in its own, so two agents can work two different issues in the same repo at once.

A session outlives the browser — close the tab, check on another initiative, come back later: the agent keeps running, and reattaching replays everything you missed.

How it works

One initiative, start to reattach

Nothing here is specific to one workflow — each step reads generic GitHub state, so it works whether or not a team follows any particular process alongside it.

  1. 1sidenav

    Pick an initiative

    The sidenav renders a project's issues as a filterable tree of initiatives and tasks — text, ship-status, and tag filters, pinning, and a live indicator when a node has an open console — so several stay in view without shoving each other out.

    ProducesTree
  2. 2flow steps

    Open an issue

    An issue's detail shows its progress as open/plan/work/review/ship, derived from plain signals — is it closed, does it have a plan, a PR, a review, a merge — plus its branch, checks, and any past Claude/Codex conversation ready to reopen.

    ProducesFlow steps
  3. 3worktree

    Launch a console

    A console starts a long-lived PTY process in a fresh git worktree or the main checkout, so an agent working this issue never touches the files another console is using for a different one.

    ProducesPTY session
  4. 4claude · codex · shell

    Hand it to an agent

    Pick claude, codex, or a plain shell, and let it do the implementation — several consoles, each with its own agent, can stay open in tabs at once.

    ProducesLive terminal
  5. 5any browser

    Check in from anywhere

    A background thread keeps draining the session's output into a buffer the whole time, so reconnecting from a new browser — after working another initiative for a while — replays everything missed instead of losing it.

    ProducesResumed

A console is not a job. It's a live process someone watches and types into, closer to a terminal you can walk away from than a task you submit and poll for a result. Progress is read, not required — the flow strip is computed from an issue's own state (closed, planned, has a PR, reviewed, merged), so it works whether or not a team runs any particular workflow behind those issues.

Multiple browsers, one session. Attaching to a session that's already running joins the existing process rather than starting a new one — its buffered output brings a fresh browser fully caught up.

Features

What's in the client

One card per component; the components themselves (client/src/app/components/) are the source — this only names the shape.

app-sidenavNavigation

Filterable tree of a project's initiatives and tasks — text, ship-status, and tag filters, pinning, and a live attention indicator when a console needs you, so juggling several at once doesn't mean losing track of any.

app-console-tabsTerminal

Multiple consoles stay open in tabs per issue or project, each backed by its own persistent PTY and its own agent choice.

app-agent-pickerTerminal

The claude/codex/shell chooser, shared between an issue's console and a project-level one.

app-session-listSessions

Past Claude/Codex conversations captured in an issue's consoles, listed on its Overview tab and reopenable to resume exactly where they left off.

app-overviewLanding

The workspace landing page: per-project issue totals — open, closed, initiatives, tasks — composed client-side from the same tree the sidenav uses.

app-usage-widgetUsage

Tracks remaining LLM usage against the engine's own cache, shifting color as a window runs low.

Reference

Engine and client, package by package

What each part of the source actually does.

Engine

Spring Boot, packaged under dev.locklane.engine: github syncs issues and PRs, pty runs the terminal processes (PtySession, SessionRegistry, OutputBuffer), ws streams terminal I/O and events to the browser over WebSocket, persistence holds SQLite and its migrations, security gates access, usage tracks LLM quota.

Client

An Angular PWA (client/) of standalone components backed by services — ProjectsService, IssuesService, ConsolesService, AgentStore — rather than a single central store.

Sessions

SessionRegistry tracks which sessions are open across engine restarts. Attaching to a session id that already has a running process joins it instead of starting a new one — a session's identity is independent of the worktree or checkout it runs in, so more than one session can point at the same directory.

Terminal environment

A session launched from a context with no real terminal attached — an IDE run configuration, systemd — gets a default TERM/COLORTERM so CLI output still gets color; an environment that already sets its own is left alone.

Storage

SQLite, configured in application.yml, with its own migration set under persistence/migration.
